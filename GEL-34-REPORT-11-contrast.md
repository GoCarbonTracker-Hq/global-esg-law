## What the test reads and how backgrounds resolve

- Colour properties read: `color`, `background(-color)`, `border*` and `border-*-color`, `outline(-color)`, `outline-offset`, `opacity` (only under `:disabled`). A colour in any other property (`box-shadow`, `text-decoration-color`, ...) fails.
- A text colour with a background in its own cascade is paired with it.
- A text colour with no background of its own: the nearest ancestor background cannot be known from CSS alone (the nesting lives in `index.html` and the JS). It is paired with both surfaces the design has, the page (`body` background, `#FFFFFF`) and the panel (`--panel` `#F7F4EC`, which is the answer panel and the tint behind the version in force). This is deliberately the strict reading: the pair is checked on a surface it may never sit on.
- A background with no text colour of its own, where the background is a surface or the colour is `inherit` (hover fill of `#example`, `.match-row`, `.rail-row`; the rail's current row; the answer panel; the narrow table header cell): paired with the `body` colour.
- A fill that is not a surface and has no text colour (the legend swatches): a `mark` row, vs the page, not counted; its border is counted as an edge.
- Edges: each border colour against both surfaces. `--divider` is decorative. A border in a surface colour that another state recolours is a spacer.
- Disabled: `:disabled { opacity: 0.6 }` blended over each surface into the text pair of every control (`input`, `button`, ...), held to 4.5 although WCAG exempts inactive controls. Result 4.74 over the page, 4.86 over the panel, so it passes either way.
- Known limit: only the controls named by element type in a selector get a disabled pair (the `input, button` rule). The Copy citation button is never disabled in `web/*.js`.

## Focus ring (what it sits against)

Ring rule: `web/style.css:56`, `outline: 2px solid var(--link); outline-offset: 2px`, the only outline rule. `--link` is `#1F6F4A`, the same colour as the Copy citation fill (`cite.css:18`).

Assumption about the offset: the 2px gap is transparent and shows whatever is painted behind the element; the ring touches a border only if the border is wider than the offset (ring starts at offset, border spans 0 to its width); with offset 0 it would touch the element's own fill and border (the test then counts those too: tried on a temp copy, `outline-offset: 0` adds ring-on-fill pairs, among them 1.00 on the Copy citation fill).

Neighbours, with the numbers:

| ring on | ratio | counted | why it is a neighbour |
|---|---|---|---|
| the page `#FFFFFF` | 6.12 | yes | the gap and the outside of any control on the page |
| the panel `#F7F4EC` | 5.57 | yes | same, inside the answer panel; this is what the Copy citation ring sits against |
| the selected row's tint (`--panel`, `rail.css:23`) | 5.57 | yes | the current row's background |
| the unselected rail row's 4px `--page` edge (`rail.css:18`) | 6.12 | yes | 4px edge is wider than the 2px offset |
| the selected rail row's 4px `--link` edge (`rail.css:23`) | 1.00 | yes, FAILS | see below |
| the Copy citation fill `--link` (`cite.css:18`) | 1.00 | no (ring-gap) | the 2px offset keeps ring and fill apart; the ring touches the panel, not the button |
| grid cell fill `--grid-stored` | 1.29 | no (ring-gap) | cells are not focusable; shown because the fill is dark green |

The failing one: the rail row is a `<button>` (`rail.js:60`) with `width:100%; border:0` inside an `li` with no padding (`rail.css:18-22, 28-39`), so its left edge sits flush against the `li`'s 4px border-left. The ring (2px gap, then 2px ring, 4px out) lies exactly over that border, which is `--link` on the current row. On the left side the ring has the same colour as what it lies on, so it merges into the selected bar; on the other three sides it shows against the page (6.12). This is a finding, not a proven user problem: no browser was run, the model is from the CSS and the HTML only.
